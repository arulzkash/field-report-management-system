# Architecture

The browser runs a React + Vite application and calls the Express REST API under `/api`. Services use Prisma to access PostgreSQL. The repository contains two independent npm packages: backend/ and frontend/.

## Request flow and modules

```text
Browser -> route -> authentication/authorization -> controller -> service -> Prisma -> PostgreSQL
```

Backend features are grouped into auth, reports, and users. Routes attach middleware; controllers validate input and build HTTP responses; services enforce business rules and query the database. Ownership is part of database queries. There is no generic repository layer or dependency injection framework.

Frontend features contain pages, components, API functions, and types. React Context holds the current session, React Router protects routes, and forms use local state. The shared fetch helper handles JSON, cancellation, timeouts, and API errors. Styling uses plain CSS.

## Data model

| Model           | Main fields                                                              | Constraints                                                                           |
| --------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| User            | id, name, email, passwordHash, role, createdAt                           | UUID; unique lowercase email; nonblank name; role enum                                |
| Session         | id, tokenHash, userId, expiresAt, createdAt                              | Unique SHA-256 token hash; User FK; user/expiry indexes                               |
| Report          | id, name, description, status, reporterId, version, createdAt, updatedAt | Pending default; positive version; nonblank content; Reporter FK and index            |
| ApprovalHistory | id, reportId, approverId, fromStatus, toStatus, reportVersion, decidedAt | Restrictive FKs; changed status; Approved/Rejected destination; unique report/version |

IDs are UUIDs. Timestamps use timestamptz; history timestamps are generated by PostgreSQL and displayed in Asia/Jakarta with a WIB label. Report and history relationships use restrictive foreign keys to preserve audit data. Sessions may cascade when a user is deleted administratively; the application exposes no deletion endpoint.

Prisma models and reviewed migrations are authoritative. `npm run db:export` concatenates ordered migration SQL into schema.sql inside one transaction, retaining custom CHECK constraints. The snapshot contains no seed data or Prisma migration bookkeeping. SQL import and migration-based setup are alternatives on empty databases; an SQL-created database needs baselining before future migration-based upgrades.

## Authentication and authorization

- Login normalizes email by trimming and lowercasing it. Passwords are preserved exactly and hashed using bcrypt cost 12. New passwords require 12-72 UTF-8 bytes, including bcrypt's maximum input boundary.
- Successful login creates a random 32-byte token and an eight-hour database session. Only its SHA-256 hash is stored in PostgreSQL; the raw token is delivered through an HttpOnly cookie.
- Cookies use SameSite=Lax and Path=/; production enables Secure. Tokens are never stored in localStorage. Successful login rotates an existing browser session; logout revokes it.
- Authentication queries the current database role and session expiry on every request. Frontend guards and hidden actions provide user feedback; backend middleware and services enforce access.
- Mutations require an Origin exactly matching APP_ORIGIN and application/json content. Missing/null/incorrect origins return 403; non-JSON writes return 415.
- Login returns the same 401 response for unknown accounts and incorrect passwords. Ten failed attempts per IP within fifteen minutes trigger 429. The limiter is in-memory for a single API process.
- User responses contain only id, name, email, and role. History exposes only the approver's id, name, and email. Password hashes and session tokens are never returned in JSON.

## API contract

Successful responses use `{ data: ... }`. Errors use `{ error: { code, message, fields? } }` without database details or stack traces.

| Method and endpoint           | Access               | Payload / result                                |
| ----------------------------- | -------------------- | ----------------------------------------------- |
| GET /api/health               | Public               | Readiness: 200, or safe 503 on database failure |
| POST /api/auth/login          | Public, valid Origin | email/password; safe user and session cookie    |
| GET /api/auth/me              | Authenticated        | Current safe user                               |
| POST /api/auth/logout         | Authenticated        | JSON `{}`; revoke session and clear cookie      |
| POST /api/reports             | Reporter             | name/description; Pending report with version 1 |
| GET /api/reports              | Reporter / Approver  | Own reports / all reports, newest first         |
| GET /api/reports/:id          | Owner / Approver     | Report details                                  |
| PATCH /api/reports/:id        | Owner, Pending       | name/description/version; updated report        |
| PATCH /api/reports/:id/status | Approver             | approved/rejected status and version            |
| GET /api/reports/:id/history  | Owner / Approver     | Decisions in ascending reportVersion order      |
| POST /api/users               | Admin                | name/email/password/role; safe created user     |

Request bodies accept only explicitly allowed fields. The server supplies owners, actors, initial status, version increments, and timestamps. UUIDs and positive integer versions are validated before queries. Lists use descending createdAt, then descending id as a tie-breaker. Auth/report/user responses disable caching.

Use 400 for invalid input, 401 for invalid sessions, 403 for forbidden roles, 404 for inaccessible/missing resources, and 409 for duplicate email or state/version conflicts. Reporters receive identical 404 responses for another owner's report and a nonexistent report. Admins do not have report access.

### Edit payload

```json
{
  "name": "Updated observation",
  "description": "Updated field details.",
  "version": 1
}
```

### Decision payload

```json
{
  "status": "approved",
  "version": 2
}
```

Use the current version from the report response. Send the authenticated cookie plus the required Origin and Content-Type headers. Successful edits/decisions return the updated report. The API does not support returning a decided report to Pending.

### Account creation payload

```json
{
  "name": "Example Reporter",
  "email": "reporter@example.test",
  "password": "Example-Reporter-Password-2026!",
  "role": "pelapor"
}
```

Roles are admin, pelapor, and approver. Names are trimmed and limited to 150 characters; emails are normalized and limited to 254 characters. PostgreSQL uniqueness handles duplicate/concurrent email creation, which returns 409 without modifying existing accounts. Account creation does not change the Admin session or reveal the assigned password.

## Concurrent edits and decisions

Editing performs a conditional update using report id, authenticated owner, Pending status, and submitted version. It increments version atomically and returns that write's row. An owner-scoped existence check classifies an unsuccessful update as 404 or 409.

A decision runs in a short transaction: read current state, validate version/transition, conditionally update id/version/status, increment version, and insert history before committing. If another write wins or history insertion fails, the transaction aborts. This prevents partial decisions and stale overwrites under PostgreSQL's default isolation.

The UI retains an edit draft after conflict and requires explicit reload before saving again. Decisions are never retried automatically. History is append-only through application endpoints and ordered by reportVersion; content edits may leave gaps in history versions. Actor names/emails reflect the current User record. Direct database administration is outside the append-only guarantee.

## Configuration and operation

Runtime settings are DATABASE_URL, PORT, NODE_ENV, and APP_ORIGIN. DIRECT_URL optionally overrides the connection used by Prisma tooling. Seed passwords are loaded only by the explicit seed script from ignored backend/.env.demo. Integration tests use ignored backend/.env.test and a database distinct from the application database.

Vite binds to localhost:5173 and proxies /api to 127.0.0.1:4000. Production hosting must serve frontend/API under the same HTTPS origin. Deployment, shared rate limiting, pagination, live updates, and advanced account management are outside the current scope.
